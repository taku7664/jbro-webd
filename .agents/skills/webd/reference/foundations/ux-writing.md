# UX 라이팅

화면의 글은 디자인 결정입니다. 버튼에 "제출"이라고 쓸지 "신청서 보내기"라고 쓸지는 사용자가 무엇을 약속한다고 믿는지를 바꿉니다. 카피가 맨 나중에 들어오면, 카피 없이 만든 틀에 억지로 끼워 맞춰집니다. 그래서 1차 구현부터 실제 문장으로 만듭니다(`build.md`).

## 기본 원칙

- **사용자에게 지금 필요한 것부터.** "우리가 하고 싶은 말"이 아니라 "이 순간 사용자가 알아야 할 것·해야 할 것". 시스템 용어(오류 코드, DB 필드명, 내부 공정 이름)를 사용자 말로 바꿉니다.
- **사람은 훑어봅니다.** 첫 구절만 읽는다고 생각하고 행동·결정·핵심 사실을 앞에 둡니다. 긴 문단 대신 짧은 문장, 목록, 단계.
- **한 개념에 한 단어.** "프로젝트·작업공간·워크스페이스"가 섞이면 사용자는 셋이 다른 것인 줄 압니다. 짧은 용어집을 만들고 화면 전체에서 지킵니다. 문학적 변주를 하지 않습니다.
- **쉬운 말**은 친절이 아니라 성능입니다. 도움 요청이 줄고 작업 완료율이 오릅니다. 다만 대상이 실제로 아는 전문 용어까지 풀어 쓰지는 않습니다.

## 목소리와 어조

| | 무엇 | 예 |
|---|---|---|
| 목소리 | 제품의 성격. 바뀌지 않음 | "직설적이고 다정하며, 비꼬지 않는다" |
| 어조 | 상황에 따라 목소리가 조절되는 정도 | 오류엔 차분하게, 완료엔 따뜻하게 |
| 높임 | 존댓말 수준 | 해요체 / 합니다체 |

- "친근하고 명확한"은 목소리가 아닙니다. 모든 브랜드가 주장하는 희망 사항입니다. 성격 형용사 3–5개를 고르고, 각각 "이건 우리 말투" / "이건 아님" 예문을 붙이고, 구체적 규칙(문장 길이, 느낌표 사용, 농담 허용 범위, 높임 수준)을 적습니다.
- **한국어 높임**: 한 제품 안에서 해요체와 합니다체를 섞지 않습니다. 소비자 서비스는 해요체가 흔하고, 공공·금융·B2B는 합니다체가 흔합니다. 버튼·라벨은 명사형이나 동사 원형("저장", "다음으로", "주문하기")으로 높임과 무관하게.

| 순간 | 어조 |
|---|---|
| 첫 빈 화면 | 맞이하고 안내, 부담 없이 |
| 오류·실패 | 차분, 분명, 해결 중심. 개성은 줄이고 정확하게. 농담 금지 |
| 완료 | 따뜻하게, 짧게 |
| 경고 | 분명하고 직접적, 겁주지 않기 |
| 파괴적 확인 | 진지하게, 결과를 구체적으로 |
| 약관·법적 고지 | 격식 있되 쉬운 말 |

## 버튼과 링크

- **동작 + 대상**: "저장", "주문하기", "프로젝트 삭제", "PDF로 받기". 결과가 뻔하면 동작만.
- "확인", "예", "제출", "클릭"을 습관처럼 쓰지 않습니다. 버튼만 읽어도 무슨 일이 일어나는지 알아야 합니다.
- 확인 대화상자는 제목과 버튼에 같은 동작 이름: 제목 "'디자인 시안'을 삭제할까요?", 버튼 "삭제" / "취소".
- 링크 글자는 맥락 없이 읽혀도 뜻이 통하게. "여기", "자세히"만으로 된 링크 금지.
- 습관적으로 붙인 `→`, "지금 바로 시작하세요!" 같은 문구는 AI 티입니다(`ai-tells.md`).

## 오류 메시지

공식: **무슨 일이 생겼나 → (필요하면) 왜 → 어떻게 고치나 → (필요하면) 다음에 무슨 일이 생기나**. 첫째와 셋째는 늘 있어야 합니다. 막다른 길을 만들지 않습니다.

| 종류 | 공식 | 예 |
|---|---|---|
| 입력 검증 | 무엇이 틀렸나 + 올바른 형식 | "이메일에 @가 빠졌어요. 예: name@example.com" |
| 로그인 | 무슨 일 + 할 수 있는 것 | "이메일이나 비밀번호가 맞지 않아요. 다시 입력하거나 비밀번호를 재설정하세요." |
| 권한 | 못 하는 것 + 이유 + 할 수 있는 것 | "편집자만 게시할 수 있어요. 관리자에게 권한 변경을 요청하세요." |
| 시스템·네트워크 | 무슨 일 + 데이터가 안전한지 + 다시 하기 | "저장하지 못했어요. 작성한 내용은 이 기기에 남아 있어요. 다시 시도해 주세요." |
| 404 | 무슨 일 + 대신 할 일 | "페이지를 찾을 수 없어요. 주소가 바뀌었을 수 있어요. 검색하거나 첫 화면으로 가세요." |

- 사용자를 탓하지 않습니다. "잘못 입력하셨습니다" → "형식이 맞지 않아요".
- 오류 코드만 보여 주지 않습니다. 코드는 사람 말 뒤 괄호에(지원 문의용).
- 오류에 느낌표·"앗!"·"이런!"을 쓰지 않습니다.
- 데이터가 안전하면 그렇다고 말합니다. 불안이 줄어듭니다.
- 모르는 원인이나 해결을 약속하지 않습니다.

## 빈 상태

| 종류 | 쓸 것 |
|---|---|
| 처음 사용 | 이 공간이 무엇을 해 주는지 + 첫 행동 버튼 |
| 사용자가 다 지움 | 다 했다는 인정 + 다음 행동 |
| 검색·필터 결과 없음 | 무엇을 찾았는지 + 다른 방법 ("'인보이스'에 대한 결과가 없어요. 철자를 확인하거나 전체 목록을 보세요.") |
| 권한 없음 | 왜 안 보이는지 + 누구에게 요청하는지 |
| 불러오기 실패 | 무엇이 있어야 하는지 + 다시 시도 |

"데이터가 없습니다."만 있는 화면은 막다른 길입니다.

## 로딩·완료

- 로딩 문구는 실제 작업 이름과 정직한 예상 시간: "보고서를 만드는 중이에요. 30초쯤 걸려요."
- 진행률을 알면 보여 주고, 모르면 지어내지 않습니다.
- 완료는 무엇이 끝났는지: "성공!" 대신 "프로필을 저장했어요". 다음에 할 일은 그게 사용자 행동을 바꿀 때만.

## 폼

- 라벨은 항상 보이게. placeholder는 예시.
- 형식·자격 요건은 제출 **전에** 알려 줍니다("비밀번호는 8자 이상").
- 왜 이 정보가 필요한지 뻔하지 않으면 설명합니다("배송 알림을 위해 휴대폰 번호가 필요해요").
- 필수·선택 표시를 일관되게. 색만으로 표시하지 않습니다.

## 도움말

- 도움말은 컨트롤 이름을 반복하지 않고, 사용자가 속으로 묻는 질문에 답합니다.
- 드문 상황의 자세한 설명은 접어 둡니다.
- 아이콘만 있는 버튼에는 접근 가능한 이름(`aria-label`)과, 가능하면 툴팁.

## 번역·접근성

- 문장 조각을 이어 붙이지 않고 완결된 문장 단위로 둡니다. 한국어는 어순이 달라서 "{n}개의 {item}을 삭제" 같은 조합이 다른 언어에서 깨집니다.
- 변수·숫자는 번역자가 순서를 바꿀 수 있게 구조로.
- 번역으로 30–40% 늘어나도 버티게 공간을 둡니다(독일어, 러시아어 등). 미리 줄여 쓰지 않습니다.
- 이미지 대체 텍스트는 이미지가 전하는 정보를. 장식이면 `alt=""`.
- 화면 낭독기가 읽는 이름이 보이는 라벨과 같아야 합니다.

## 피할 말

- 상투적 홍보 문구: "혁신적인", "차원이 다른", "세계 최고 수준의", "완벽한 솔루션", "게임 체인저" (검출기 `buzzword-copy`)
- 억지 대비: "단순한 앱이 아닙니다. 당신의 파트너입니다."
- 근거 없는 수치·고객사·후기. 없으면 자리 표시로 남기고 알립니다.

## 확인

- 버튼만 읽어도 무슨 일이 일어나는지 아는가?
- 모든 오류가 무엇이·어떻게를 말하는가? 막다른 오류가 없는가?
- 빈 상태마다 다음 행동이 있는가?
- 같은 개념에 같은 단어를 쓰는가? 높임이 섞이지 않았는가?
- 번역으로 길어져도 버튼·라벨이 깨지지 않는가?
