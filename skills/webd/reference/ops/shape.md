# shape — 만들기 전에 브리프부터

코드를 쓰거나 시각 방향을 고르기 전에, 무엇을 왜 만드는지를 짧은 브리프로 정리합니다. 요청이 한두 문장으로 흐릿하게 왔을 때 특히 씁니다.

## 1단계: 인터뷰

- 한 번에 **2–3개의 관련 질문**을 묻고 답을 기다립니다. 질문지를 한꺼번에 쏟지 않습니다.
- 기본은 한 라운드. 답에서 중요한 빈칸이 드러날 때만 두 번째 라운드.
- 이미 정해진 것을 다시 묻지 않고, 뻔한 것은 "이렇게 이해했는데 맞나요?"로 확인만 합니다.
- 질문 도구(AskUserQuestion 등)가 있으면 씁니다.
- CSS 값이나 "미니멀 vs 화려" 같은 정해진 미학 선택지는 묻지 않습니다. 시각 방향은 `direction.md`가 맡습니다.

**1라운드: 목적·사람·결과** (가장 결과를 바꾸는 2–3개)
- 이 화면·기능은 무엇을 위해 있고 어떤 문제를 풀어야 하나?
- 누가, 어떤 상황·기분으로 여기에 오나?
- 그 사람이 반드시 이해하거나 해야 할 한 가지는? 성공은 어떤 모습인가?
- 이웃 제품이나 일반 템플릿은 주장할 수 없는, 여기만의 진실은 무엇인가?

**2라운드: 재료·동작·경계** (중요한 미정 사항이 있을 때만)
- 실제 콘텐츠·근거·데이터·자산은 무엇이고, 최소·보통·최대 범위는?
- 중요한 상태와 전환: 첫 실행, 빈 상태, 로딩, 오류, 성공, 권한, 넘침, 숙련자 사용
- 사용자가 만들거나 고치는 대상이 있다면: 언제 저장되고, 무엇을 잃을 수 있고, 판단하려면 무엇을 나란히 봐야 하나 (`structure.md`)
- 원하는 완성도와 범위: 탐색용 시안, 출시 가능한 화면 하나, 전체 흐름, 더 넓은 영역
- 반드시 그대로 둘 것은? 다듬어져 보여도 "틀렸다"고 느끼게 할 것은?
- 플랫폼·프레임워크·성능·접근성·다국어·배포 제약

## 2단계: 여정과 구조 (흐름이 여러 화면일 때)

- **할 일 문장(JTBD)**: "___할 때, 나는 ___하고 싶다, 그래서 ___할 수 있게." 기능이 아니라 상황과 동기로.
- **흐름**: 진입 → 주 작업 단계 → 완료 → 다음. 각 단계에서 사용자가 알아야 할 것·결정할 것.
- **정보 구조**: 화면 목록과 각 화면의 책임, 내비게이션 단위, 이름(라벨).
- **페이지 명세**: 화면마다 목적, 주 행동, 필요한 콘텐츠 블록 순서, 상태 목록.

주의할 함정:
- 여정 지도를 그리는 것 자체가 목적이 되는 것 (결정에 쓰이지 않는 지도는 장식)
- 사용자가 직선으로 깔때기를 따라간다는 가정 (실제로는 오가고 비교하고 미룸)
- 다른 서비스의 랜딩 구조를 이유 없이 복제하는 것
- "첫 화면 아래는 아무도 안 본다"는 믿음 (사람들은 스크롤합니다. 다만 첫 화면이 계속 볼 이유를 줘야 합니다)

## 3단계: 브리프 작성

`PRODUCT.md`를 채우거나 갱신하고, 이번 작업의 브리프를 아래 형식으로 씁니다(저장 위치: `.webd/briefs/<화면>.md`, 사용자가 원하면).

```markdown
# <화면 이름> 브리프

목적: 한 문장
누구: 누가, 어떤 상황에서
성공: 사용자가 이 화면에서 ___하면 성공
모드: Persuade / Operate / Read / Experience
구조: `structure.md` 일곱 질문의 답 → 유형
여기만의 진실: 템플릿이 주장할 수 없는 것

## 콘텐츠
- 실제로 있는 것: …
- 없어서 자리 표시할 것: …
- 범위: 최소 … / 보통 … / 최대 …

## 상태
첫 실행, 빈, 로딩, 오류, 성공, 권한 …

## 범위와 경계
- 만들 것: …
- 그대로 둘 것: …
- 틀렸다고 느껴질 것: …

## 제약
…

## 미정
…
```

## 확인하고 멈춘다

브리프를 사용자에게 보여 주고 확인을 받습니다. 확인 전에는 시각 방향도 코드도 시작하지 않습니다. 확인되면 `direction.md`로 넘어갑니다.
