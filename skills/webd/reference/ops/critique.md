# critique — 점수 매긴 디자인 비평

디자인 디렉터처럼 화면을 평가하고, **무엇이 이 화면을 붙잡고 있는지**를 우선순위와 함께 보고합니다. 고치라는 요청이 없으면 코드를 바꾸지 않습니다.

## 준비

1. `PRODUCT.md`·`DESIGN.md`가 있으면 읽습니다. 화면 모드(`reference/modes.md`)를 확인합니다.
2. 실제 화면을 봅니다. 브라우저 도구가 있으면 375·1440px 스크린샷, 주 작업 경로를 직접 따라가 봅니다. 없으면 소스만 봤다고 보고 첫 줄에 적습니다.
3. 평가는 두 갈래로 따로 합니다. **기계 검사 결과를 보기 전에** 디자인 판단을 먼저 적어서, 검사 결과가 판단을 끌고 가지 않게 합니다.
   - A. 디자인 판단 (아래 1–6)
   - B. 기계 검사: `scripts/detect.mjs`, `scripts/render-check.mjs`
4. 둘을 합칠 때 겹친 것, A만 찾은 것, B만 찾은 것, B의 오탐을 구분합니다.

## A. 디자인 판단

### 1. 이 제품의 것인가 (가장 먼저)

같은 화면을 다른 제품에 그대로 붙여도 말이 되면, 이 화면은 아무 결정도 하지 않은 것입니다. 확인할 것:

- 구조가 카테고리 기본형(히어로 → 아이콘 카드 3개 → 후기 → CTA)과 같은가?
- 사용자가 무언가를 만들거나 고치는 화면인데 홈페이지처럼 짜였는가? (`structure.md`「페이지형 쏠림 점검」)
- 도구 화면이 구조는 맞는데 이름을 가리면 어느 분야 도구인지 모르는가? (`modes.md`「Operate에서 주제 세계 드러내기」: 결과 영역·단위·상태 기록에 세계가 있는가)
- 서체·색·구성 중 이 제품의 주제 세계에서 나온 결정이 있는가?
- 시그니처 요소가 실제로 보이는가?
- `ai-tells.md` 항목이 근거 없이 쓰였는가?

판정: **고유함 / 부분적 / 교체 가능** 중 하나와 근거 두세 줄.

### 2. 전체 디자인

위계와 정보 구조, 감정적 적합성, 찾기 쉬움, 구성, 타이포, 색, 접근성, 상태, 카피, 극단 상황. 각 항목의 판단 기준은 `foundations/` 문서들입니다.

### 3. 인지 부하

| 점검 | 실패 조건 |
|---|---|
| 한 가지 초점 | 주 작업을 하는 동안 경쟁하는 요소가 시선을 빼앗음 |
| 덩어리 | 한 묶음에 정보가 5개 이상 |
| 묶음 | 관련된 것이 시각적으로 묶이지 않음 |
| 위계 | 가장 중요한 것이 바로 안 보임 |
| 한 번에 하나 | 결정 두 개를 동시에 요구 |
| 적은 선택 | 한 결정 지점에 보이는 선택지 5개 이상 |
| 작업 기억 | 앞 화면의 정보를 기억해야 이 화면에서 행동 가능 |
| 점진적 공개 | 필요 없는 복잡성이 처음부터 다 보임 |

실패 0–1: 낮음, 2–3: 보통(곧 손볼 것), 4 이상: 높음(시급).

### 4. 감정의 흐름

- 주 작업에서 가장 강한 순간(정점)과 끝이 좋게 남는가? (`usability.md` 정점-끝)
- 불안한 순간(결제, 삭제, 개인정보 입력)에 안심시키는 정보가 있는가?
- 실패·빈 상태가 막다른 길인가?

### 5. 휴리스틱 점수

Nielsen 10가지(`usability.md`)를 각각 0–4점으로 매깁니다.

| 점수 | 기준 |
|---|---|
| 0 | 전혀 지켜지지 않음, 사용자가 추측해야 함 |
| 1 | 드물게만 지켜짐 |
| 2 | 부분적, 큰 빈틈 있음 |
| 3 | 대체로 좋음, 작은 빈틈 |
| 4 | 뛰어남. 아낌없이 주는 점수가 아님 |

- Persuade·Experience 화면(랜딩, 캠페인, 포트폴리오)에서는 7(유연성·효율)과 10(도움말)을 `해당 없음`으로 둘 수 있습니다. 한 줄 이유를 쓰고 만점을 그만큼 줄입니다(예: 8개만 매기면 /32).
- 등급은 비율로 읽습니다: 90% 이상 뛰어남, 70% 이상 좋음, 50% 이상 보통, 30% 이상 나쁨, 그 아래 심각.
- 실제 화면 대부분은 50–80% 사이입니다. 점수를 부풀리지 않습니다.

### 6. 페르소나로 걸어 보기

화면 성격에 맞는 2–3명을 고르고, 주 작업을 그 사람으로 직접 해 봅니다. 일반론이 아니라 **무엇이 그 사람에게서 깨졌는지** 요소 이름으로 씁니다.

| 페르소나 | 특징 | 확인할 것 | 고를 때 |
|---|---|---|---|
| **숙련자** | 비슷한 도구에 익숙, 안내를 건너뜀, 느리면 떠남 | 단축키, 일괄 작업, 건너뛸 수 있는 안내, Esc로 닫기, 60초 안에 주 작업 | 업무 도구, 대시보드 |
| **처음 쓰는 사람** | 지시를 꼼꼼히 읽음, 낯선 것 앞에서 망설임, 용어를 문자 그대로 이해 | 5초 안에 첫 행동이 보이나, 아이콘에 글자, 결정 지점의 도움말, 되돌리기, 완료 확인 | 거의 모든 화면 |
| **키보드·화면 낭독 사용자** | 마우스 없이 이동, 제목·랜드마크로 탐색 | 포커스 표시, Tab 순서, 라벨, 상태 알림, 건너뛰기 링크 | 모든 화면 (기본 포함 권장) |
| **바쁜 모바일 사용자** | 한 손, 짧은 주의, 불안정한 네트워크 | 엄지 영역의 주 행동, 큰 터치 대상, 느린 네트워크에서의 로딩·실패 | 소비자 서비스, 결제 |
| **의심 많은 결정자** | 비교하고 근거를 찾음, 숨긴 조건을 싫어함 | 가격·조건이 결정 지점에 보이나, 주장에 근거가 있나, 해지·환불 방법 | 랜딩, 가격, 가입 |

`PRODUCT.md`의 대상에서 이 프로젝트만의 페르소나를 1–2명 더 만들 수 있습니다.

## 보고서 형식

채팅에 아래 전체를 씁니다(요약 한 줄로 대신하지 않음). 사용자가 원하면 `.webd/critique/<날짜>-<대상>.md`로도 저장합니다.

```markdown
방법: 렌더 확인(375·1440) + 소스 + detect/render-check   ← 화면을 못 봤으면 "소스만 확인"이라고 첫 줄에

## 고유성 판정
판정: 부분적
- 근거 …

## 전체 인상
무엇이 되고 무엇이 안 되는지, 가장 큰 기회 하나

## 휴리스틱 점수
| # | 휴리스틱 | 점수 | 핵심 문제 |
|---|---|---|---|
| 1 | 시스템 상태 | 3 | … |
| … | | | |
| 합계 | | 26/40 (65%, 보통) | |

## 잘 된 것 (2–3개, 왜 되는지)

## 우선 문제 (3–5개, 중요한 순서)
- [P1] 무엇: …
  - 왜 중요한가: …
  - 고칠 방법: … (구체적으로)
  - 맞는 명령: layout / clarify / …

## 인지 부하
실패 n개: … / 선택지가 5개 이상인 결정 지점: …

## 페르소나별 걸림
**처음 쓰는 사람**: …

## 기계 검사
detect: high n, medium n (겹침 / 새로 찾음 / 오탐)
render-check: …

## 작은 관찰

## 생각해 볼 질문
- 주 행동이 더 눈에 띈다면?
- 이게 이렇게 복잡해야 하나?
```

## 심각도

| 등급 | 뜻 | 처리 |
|---|---|---|
| P0 | 막힘. 작업을 끝낼 수 없음 | 바로 고침 |
| P1 | 큰 어려움·혼란 | 출시 전 고침 |
| P2 | 불편하지만 우회 가능 | 다음 손질 때 |
| P3 | 다듬기 | 여유 있을 때 |

## 끝난 뒤

- 사용자에게 무엇부터 고칠지 묻습니다. 기본 제안은 P0·P1을 다루는 명령 순서.
- 같은 대상을 다시 비평하면 이전 점수와 비교해 무엇이 나아졌는지 함께 보고합니다.
