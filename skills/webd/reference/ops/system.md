# 시스템 명령: extract · document

잘 나온 화면을 반복 가능한 체계로 바꾸는 명령입니다. 판단 기준은 `foundations/design-systems.md`.

---

## extract — 반복되는 것을 토큰·컴포넌트로

1. **기존 체계 찾기**: 디자인 시스템·컴포넌트 폴더, 토큰 파일, 명명 관습, import 관습을 확인합니다. 체계가 없으면 아직 만들지 않고 위치·구조를 먼저 묻습니다.
2. **패턴 찾기**
   - 같은 의도로 **3번 이상** 쓰인 컴포넌트(버튼, 입력, 행, 빈 상태)
   - 토큰이어야 할 하드코딩 값(색, 간격, 글자 조합, 그림자, 이징·길이)
   - 같은 개념의 여러 구현
   - 반복되는 구성(폼 한 줄, 도구 모음, 빈 상태 블록)
   - 2번 이하로 쓰인 것은 뽑지 않습니다. 성급한 추상화는 중복보다 나쁩니다.
3. **계획**: 뽑을 컴포넌트, 만들 토큰(원시/의미 구분), 필요한 변형, 이름, 기존 사용처를 옮기는 순서. 사용자에게 보여 주고 진행합니다.
4. **뽑고 다듬기**: 분명한 props와 기본값, 실제로 필요한 변형만, 접근성 내장(이름·역할·키보드·포커스), 모든 상태.
5. **옮기기**: 모든 사용처를 찾아 새 컴포넌트·토큰으로 바꾸고, 바뀌기 전후 화면이 같은지 렌더로 확인하고, 옛 구현을 지웁니다.
6. **기록**: `DESIGN.md`의 해당 절을 갱신합니다.

**한 화면에서 시스템 키우기**(direction 경로 D)도 같은 절차입니다. 그 화면의 계산된 값(브라우저에서 `getComputedStyle`)까지 읽으면 토큰이 놓친 값도 잡힙니다.

---

## document — DESIGN.md 쓰기

기존 코드에서 디자인 체계를 읽어 `DESIGN.md`로 남깁니다. 이미 있으면 덮어쓰지 않고 차이를 보여 준 뒤 갱신합니다.

### 1. 자산 찾기 (우선순위 순)

1. CSS 변수: `--color-`, `--font-`, `--space-`, `--radius-`, `--shadow-`, `--ease-`, `--duration-`
2. Tailwind 설정의 `theme.extend`
3. CSS-in-JS 테마 파일(`theme.ts`, `tokens.ts`)
4. 토큰 파일(`tokens.json`, Style Dictionary 출력)
5. 주요 컴포넌트(버튼, 카드, 입력, 내비, 대화상자)의 기본 스타일과 변형
6. 전역 스타일시트의 기본 글자·색
7. 렌더된 화면의 계산값(브라우저 도구가 있으면 body, h1, a, button 등에서 샘플)

### 2. 자동으로 뽑을 수 있는 것

- 색: 역할별로(주·보조·무채색·상태). 포인트가 하나뿐이면 보조를 지어내지 않습니다.
- 글자: 역할별 패밀리·크기·굵기·행간, 스케일 비율, 한글 설정
- 깊이: 그림자 단계. 그림자 없이 면 밝기로 층을 나누는 프로젝트면 그렇다고 적음
- 컴포넌트: 반경, 색 배정, hover·focus 처리, 안쪽 여백
- 레이아웃: 그리드, 컨테이너 폭, 브레이크포인트, 간격 리듬, 밀도
- 모양: 반경, 모서리, 테두리 규칙

없는 것은 비워 둡니다. 지어낸 토큰은 명세를 오염시킵니다.

### 3. 사용자에게 물어야 하는 것

자동으로 뽑을 수 없는 질적 언어. 2라운드, 라운드당 3개 이하.

- 이 제품의 시각적 성격을 세 단어로? (예시를 들어 주되 고르게 하지 않음)
- 레퍼런스나 영감이 된 것이 있나?
- 절대 하지 않을 것은?
- 이 프로젝트만의 규칙이 있나? ("주 행동 색은 한 화면에 한 곳")

### 4. 쓰기

`templates/DESIGN.md` 형식, 절 순서는 `design-systems.md`의 "DESIGN.md에 들어갈 것"을 따릅니다. 색 값은 프로젝트가 쓰는 형식 하나로(OKLCH 또는 hex), 같은 토큰을 두 형식으로 적지 않습니다.

### 5. 확인

- 문서의 값이 실제 코드 값과 같은가? (몇 개를 골라 대조)
- 대비 표를 `check-style.mjs` 형식(`contrast` 블록)으로 넣었다면 통과하는가?
