# 검증

검증은 세 겹입니다. 앞 단계가 못 잡는 것을 뒤 단계가 잡습니다.

## 1. 자동 검사

```
node "<스킬 폴더>/scripts/detect.mjs" <파일 또는 폴더> [--allow 규칙,규칙] [--json]
```

- 의존성 없는 Node 스크립트입니다. 정규식으로 찾을 수 있는 항목만 봅니다(`--list-rules`로 목록 확인).
- `DESIGN.md`에서 사용자가 고정한 결정은 `--allow`로 뺍니다. 예: 사용자가 글래스모피즘 스타일을 골랐으면 `--allow glassmorphism`. 사용자가 고정하지 않았어도 `DESIGN.md`「고정」에 이유와 함께 적은 디자인 결정(예: 장부식 합계 위 이중선)은 `--allow`로 뺄 수 있습니다(우선순위 3이 4보다 위). 이유 없이 지적을 끄는 데 쓰지 않습니다.
- 종료 코드: 0 = high·medium 없음, 2 = 있음, 1 = 사용 오류.
- 결과는 `ai-tells.md` 항목과 대응시켜 정리합니다. **0건이어도 "AI 티 없음"이라고 단정하지 않습니다.** 카드 반복, 위계, 대비, 숨김 처리 같은 항목은 렌더에서만 보입니다.
- 프로젝트에 Impeccable이 이미 설치돼 있으면 `npx impeccable detect`를 함께 써도 됩니다. 새로 설치·다운로드가 필요하면 사용자 승인을 먼저 받습니다.

## 2. 렌더 확인

브라우저·스크린샷 도구가 있으면 실제 화면을 봅니다.

- 해상도: 375px, 768px, 1440px. 가능하면 1024px도
- 라이트·다크 모드(지원하는 경우)
- 키보드 Tab으로 포커스 이동
- **애니메이션이 끝난 뒤에** 찍습니다. 진입 연출 도중의 화면을 보고 깨졌다고 판단하지 않습니다. 가능하면 `element.getAnimations()`로 끝났는지 확인합니다.
- 화면 글자 크기는 눈대중 대신 계산합니다(특히 SVG 라벨, `clamp()` 제목).
- 확인한 것과 확인하지 못한 것을 나눠 기록합니다.

한 번 볼 때 여러 문제를 함께 찾고, 몰아서 고친 뒤 다시 봅니다. 수정 하나마다 스크린샷을 찍지 않습니다.

## 3. 비평

렌더를 보고 디자이너 입장에서 평가합니다. 자기 결과물이라고 너그럽게 보지 않습니다.

**마지막 비평은 다른 눈으로 합니다.** 서브에이전트를 쓸 수 있으면 만든 대화를 넘기지 않은 새 에이전트에게 스크린샷(첫 화면·전체, 넓은·좁은 폭), `PRODUCT.md`, `DESIGN.md`, 원래 요청, `visual-quality.md` 경로만 주고 비평을 받습니다. 만든 쪽의 설명을 넘기지 않습니다(설명이 판단을 끌고 갑니다). 서브에이전트가 없으면 만든 과정을 내려놓고 스크린샷만 보며 `visual-quality.md` 9절 질문에 답합니다. 비평에서 "정돈 수준이 기준 제품보다 떨어진다"가 나오면 수치 검사가 모두 통과여도 완성이 아닙니다.

비평가에게는 판정을 셋 중 하나로 받습니다: **기준 이상 / 비슷함 / 떨어짐**, 그리고 지적마다 높음·중간·낮음. 다음 중 하나면 고친 뒤 **새 비평가에게 다시** 비평받습니다(최대 2회): 판정이 "떨어짐", 또는 "높음" 지적이 하나라도 있었음. "비슷함"에 높음 지적이 없으면 중간 지적을 고치고 마칩니다. 2회를 다 쓰고도 마지막 비평에 높음 지적이 있었다면, 고친 뒤 "고쳤으나 재비평 못 함"으로 보고에 남깁니다(통과로 적지 않음). 비평가끼리 의견이 반대면 `PRODUCT.md`의 사용 상황에 맞는 쪽을 택하고 이유를 적습니다. 다시 비평받을 때도 앞 비평 내용은 넘기지 않고 새 스크린샷만 줍니다.

- **첫인상**: 3초 안에 무엇을 하는 화면인지 보이는가. 시선이 처음 가는 곳이 의도한 곳인가.
- **브리프 대조**: `PRODUCT.md`의 목표와 `DESIGN.md`의 금지 조건을 지켰는가. 요구사항이 화면에서 바로 찾아지는가.
- **구조 대조**: `PRODUCT.md`「구조」 칸의 답에서 나온 "꼭 넣을 것"이 다 있는가(`structure.md`). 대상이 있는 화면이면 「페이지형 쏠림 점검」 항목이 하나도 없는가. 저장·되돌리기·제출 같은 동작은 화면만 보지 말고 실제로 눌러 상태가 맞게 바뀌는지 봅니다(저장 중 제출이 막히는지 등). 브라우저 도구가 없으면 `render-check.mjs`가 내보내는 `launch`·`connect`(CDP)를 import해 작은 시험 스크립트로 누릅니다. 첫 화면 확인은 `render-check --height 800 --out <폴더>`가 저장하는 `<폭>-<모드>-first.png`로 봅니다. `render-check`가 "대화상자 자동 수락: beforeunload"를 보고하면 나가기 경고가 동작한다는 뜻입니다.
- **시그니처**: 이 프로젝트에서만 나올 결정이 실제로 보이는가. 같은 브리프로 다른 모델이 만들어도 똑같이 나올 화면인가.
- **하한선**: `craft-floor.md` 위반
- **AI 티**: `ai-tells.md` 대조. 근거 없는 항목만 올립니다.
- **덜어낼 것**: 빼도 나빠지지 않는 요소 하나

## 지적을 수정 스펙으로

지적은 "더 세련되게" 같은 말로 남기지 않고 바로 실행할 수 있는 스펙으로 바꿉니다.

```
- 위치: 가격 섹션 카드 3개
- 문제: 같은 크기 카드 반복, 추천 플랜이 구분되지 않음
- 수정: 추천 플랜만 1.2배 너비 + primary 테두리 2px, 나머지 그림자 제거
- 근거: ai-tells.md 페이지 뼈대 1번, DESIGN.md 금지 조건 2번
```

수정 범위가 크면 이 스펙 목록을 서브에이전트에 나눠 줄 수 있습니다. 같은 파일을 두 작업이 동시에 고치지 않게 나눕니다.
